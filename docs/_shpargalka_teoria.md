# Шпаргалка: ТЕОРИЯ (на случай вопросов)

Каждый блок: простое объяснение вслух + точные факты (авторы, годы, цифры).

---

## 1. СППР (DSS) и зачем тут LLM
**Вслух:** СППР — интерактивная система, которая помогает человеку принимать решения в
слабоструктурированных задачах. Классически у неё три подсистемы: данные, модели,
интерфейс. LLM радикально меняет интерфейс — раньше нужен был SQL или формальная команда,
теперь диалог на естественном языке, и часть функций «движка» (подбор источников, синтез
ответа) берёт на себя модель.
**Моя СППР** = информационно-аналитическая (Data-Driven DSS). ЛПР — инженер-оператор /
начальник смены. Работает с двумя классами знаний: **семантические** (нормативка) и
**фактологические** (состояние парка).

### Ограничения «голой» LLM → почему нужен RAG
1. знания ограничены датой обучения (cutoff), нет корпоративных данных;
2. галлюцинации — правдоподобная, но неверная информация;
3. нет доступа к актуальному состоянию объектов;
4. нельзя класть конфиденциальные документы в обучающую выборку (безопасность).
→ RAG: документы лежат во внешнем хранилище, подключаются только в момент запроса.

## 2. RAG — Retrieval-Augmented Generation
**Вслух:** Модель получает на вход не только вопрос, но и релевантные куски внешних
документов, найденные поиском. Это позволяет работать с корпоративными данными без
дообучения модели.
**Автор:** П. Льюис (Lewis P.) и соавт., 2020.
**Три поколения** (обзор И. Гао / Gao Y., 2023):
- **Naive RAG** — базовая схема embed → search → generate.
- **Advanced RAG** — переформулировка запроса, переранжирование, фильтрация контекста.
- **Modular RAG** — компонентная архитектура с агентом, function calling, несколько источников.
**Я выбрал Modular RAG** — потому что нужен агент, работающий с двумя источниками
(документы + база парка).

---

## 3. ReAct — Reasoning + Acting
**Вслух:** Паттерн, при котором агент рассуждает и действует пошагово: на каждом шаге —
мысль (Thought), действие/вызов инструмента (Action), результат (Observation), и так по
кругу, пока не соберёт достаточно информации для финального ответа.
**Авторы:** Ш. Яо (Yao S.) и соавт., 2022. Превосходит чистый Chain-of-Thought на задачах,
где нужны внешние источники.
**В моей системе:** реализован через нативный function calling LangChain (а не текстовый
парсинг Action/Observation — он хрупкий для gpt-4o-mini). Трасса шагов видна через
intermediate_steps.
**Пример:** «давно ли осматривался ТМ-630/10-2 и что требует ПТЭЭП» → агент сначала
query_equipment_db (дата + расчёт просрочки), потом search_documentation (норма). Чистый
RAG так не умеет — он только цитирует документы.

## 4. Гибридный поиск
**Вслух:** Объединяю два вида поиска. Плотный (векторный) понимает смысл и синонимы, но
«размывается», когда в запросе много лишних слов. Лексический (полнотекстовый) ловит точные
термины и аббревиатуры, но пропускает синонимы и словоформы. Вместе они компенсируют
слабости друг друга.
| Метод | Принцип | Слабость |
|---|---|---|
| Плотный (dense) | косинус эмбеддингов | семантическое размытие на «шумных» запросах |
| Лексический (sparse) | FTS, ts_rank | пропускает синонимы и парафразы |
| Гибрид с RRF | слияние по обратным рангам | сложнее реализация, два индекса |
**Семантическое размытие (semantic dilution):** при запросе с кучей слабосвязанных слов
эмбеддинг превращается в усреднённую точку, далёкую от любого конкретного фрагмента.
Пример из работы: «осмотр трансформатор масляный силовой» — нужный п. 2.1.34 ПТЭЭП (с.53)
выпадал за топ-15; слова «масляный/силовой» подтягивали разделы про масло. По теме
(«периодичность осмотра трансформаторов без отключения») — фрагмент встаёт на 1 место.

## 5. RRF — Reciprocal Rank Fusion
**Вслух:** Метод слияния двух списков результатов по позициям (рангам), а не по «сырым»
оценкам. Это его сила — косинус и tf-idf несравнимы напрямую, а ранги — сравнимы.
**Формула:** RRF(d) = Σᵢ 1 / (k + rankᵢ(d)), где rankᵢ — позиция документа в i-м списке, k —
сглаживание, у меня **k = 60** (стандарт).
**Авторы:** Г. Кормак (Cormack G.), Кларк, Бюттхер, 2009.
**Почему RRF, а не нормализация оценок / learning-to-rank:** не требует приведения к единой
шкале и не требует размеченной обучающей выборки — идеально для прототипа.

## 6. pgvector + HNSW
**Вслух:** pgvector — расширение PostgreSQL для хранения векторов и поиска по близости.
Оператор `<=>` — косинусное расстояние. Чтобы не сканировать всё, строится индекс HNSW.
**HNSW** (Malkov, Yashunin, 2020) — многоуровневый граф: верхние уровни для грубой
навигации, нижние — для точного уточнения. Параметры: **m** (рёбер на вершину),
**ef_construction** (качество ↔ память).
Лексическая ветка: tsvector + GIN-индекс, русский словарь (ispell + snowball), ts_rank_cd.

## 7. Конвейер обработки документов (RAG-pipeline)
1. Загрузка PDF — PyPDFLoader.
2. Очистка — колонтитулы, переносы, лишние пробелы.
3. Чанкинг — RecursiveCharacterTextSplitter, **до 1500 символов, overlap 300**; для ГОСТ/РД
   регулярка держит пункт целиком в одном чанке.
4. Эмбеддинги — **text-embedding-3-small, размерность 1536**, пакетами по 100.
5. Запись в БД, **id = SHA-256 содержимого** → идемпотентность повторного запуска.

## 9. Архитектура системы (4 слоя)
- **Представление** — Streamlit (чат + трасса ReAct).
- **Прикладная логика** — FastAPI (маршрутизация).
- **Агент** — LangChain, gpt-4o-mini, function calling, 2 инструмента.
- **Данные** — PostgreSQL 16 + pgvector (векторы фрагментов + таблица equipment).

## 10. Почему расчёт просрочки — в коде, а не в LLM
**Вслух:** Языковые модели плохо считают арифметику с датами — могут ошибиться. Поэтому
сравнение дат и расчёт «возраста» осмотра делает код инструмента query_equipment_db
детерминированно, а модель занимается только языком. Это общий принцип надёжных агентских
систем: детерминированные вычисления — в коде, языковая обработка — в модели.
